# QuietFix 역할별 접근 제어

ACP 모드는 선택적으로 켠다. 기본값 `QF_ACP_ENABLED=0`에서는 기존 개발 명령과 관리자 Originator를 유지한다. 데이터셋, 임계값, 샘플 ID, 수집 주기, 상태 파일 형식은 변경하지 않는다. ACP는 CSE 리소스 권한을 바꾸므로 활성화 후 테스트 주입기는 수집기 신원이나 관리자를 사용해야 한다.

## 권한

| 리소스 | 생성 | 조회와 발견 | 추가 권한 |
|---|---|---|---|
| MN 수집기와 머신 컨테이너 | 수집기: CNT와 CIN | 수집기, 분석기, 백업 관리 AE | 분석기와 백업 관리 AE는 SUB만 생성 |
| MN 분석 결과 | 분석기: CIN | 분석기, 백업 관리 AE | 백업 관리 AE는 SUB만 생성 |
| IN archive | 백업 관리 AE: CNT, CIN, GRP | 백업 관리 AE, 대시보드 | 그룹에는 별도 ACP와 macp 적용 |
| IN telemetryGroup | 백업 관리 AE가 상위 archive에 생성 | 백업 관리 AE, 대시보드 | 백업 관리 AE만 그룹 갱신 |
| qf-analyzer 구독 | 분석기 | 분석기 | 분석기만 구독 갱신 |
| qf-forwarder 구독 | 백업 관리 AE | 백업 관리 AE | 백업 관리 AE만 구독 갱신 |
| ACP 자체 | 관리자 | 참조에 필요한 역할 | 변경과 삭제는 관리자만 |

모든 ACP에 관리자 유지보수 권한이 포함된다. 생성 권한은 `acod/chty`로 자식 리소스 타입을 제한한다. 분석기가 구독을 만들 수 있다는 이유로 센서 CIN까지 생성할 수 있게 하지 않는다. 신규 머신 컨테이너와 구독, 그룹에도 명시적으로 정책을 연결한다. 기존 CIN은 수정하지 않고 부모 컨테이너의 접근 제어를 따른다.

## 적용 순서

1. 현재 ACME 설정과 리소스 데이터를 백업한다. 워커를 일시 정지하고 별도 시험 인스턴스에서 먼저 수행한다. CSE 접근 제어 검사가 켜져 있어야 한다.
2. 기존 `session.env`를 읽고 관리자 Originator를 확인한다. 다음 명령은 CSE의 QuietFix 권한을 실제 변경한다.

```bash
source session.env
export QF_ADMIN_ORIGIN=CAdmin
python apps/access_control.py --apply
```

프로그램은 AE를 준비하고 실제 `aei`와 역할별 Originator를 비교한다. 값이 다르면 출력된 AE-ID를 해당 `QF_*_ORIGIN`으로 설정하고 재실행한다. 백업 관리 AE는 MN에 등록한다. IN ACP는 MN에서 전달되는 `/id-quietfix-mn/Cqfforwarder` 신원을 허용한다. IN의 기존 forwarder 리소스는 호환성을 위해 남아 있지만 런타임에서 직접 접속하지 않는다. 정책은 한 수집기 `QF_COLLECTOR_ID`를 대상으로 적용하므로 여러 수집기는 각 ID와 Originator를 지정하여 순차 적용한다. 분석기·백업 관리 AE·대시보드 Originator는 수집기마다 변경하지 않는다.

3. 실제 CSE에서 허용과 거부를 확인한다.

```bash
python apps/verify_access.py --run
```

임시 컨테이너에 시험 CIN을 생성하고 역할별 조회·금지된 생성·삭제·ACP 변경·acpi 변경을 확인한 뒤 관리자 권한으로 임시 컨테이너를 정리한다. 403 이외의 실패는 권한 검증 성공으로 취급하지 않는다. 강제 종료 시 `qf-acp-check-` 임시 컨테이너가 남을 수 있다.

4. 모든 앱 터미널의 환경에 다음 값을 적용하고 기존 명령으로 재시작한다.

```bash
export QF_ACP_ENABLED=1
```

구독 알림, 구독 URL 변경, 그룹 최신값 일괄 조회, 새 머신 자동 등록을 확인한다. 새 게이트웨이 AE 자체는 관리자가 먼저 등록해야 하지만 등록된 수집기 아래의 새 머신은 기존 자동 생성 흐름을 유지한다. 기존 테스트 JSON을 수정하거나 교체하는 방법도 같다.

## 기존 데이터와 개발 환경

- 기존 리소스의 `acpi`는 제한 정책 한 개로 교체한다. 그룹의 `macp`도 설정한다. 다른 permissive ACP를 함께 유지하지 않는다.
- 데이터 내용이나 로컬 상태 파일을 삭제하지 않는다. 데이터셋 변경 시 기존 replay-id 규칙을 그대로 따른다.
- 기본 관리자 개발 모드는 적용 후에도 유지보수 권한으로 동작한다. `QF_ACP_ENABLED=0`은 앱의 요청 신원 선택만 바꾸며 CSE의 ACP를 제거하지 않는다.
- 기존 ACP로 완전히 복원하려면 백업한 리소스별 acpi와 macp를 관리자로 복원한다. 권한 이전은 여러 요청이므로 트랜잭션이 아니다. 실패 시 워커를 정지한 상태로 원인을 수정하고 재실행하거나 백업으로 복원한다.
- 알 수 없는 기존 구독이나 검색 한도 도달은 자동으로 무시하지 않고 중단한다. 로그를 검토한다. 범위 밖 리소스나 CSEBase 정책은 바꾸지 않는다.

## 보안 범위와 평가 근거

이 변경은 역할별 권한 분리다. Originator 헤더 자체는 인증 수단이 아니다. 실제 운영에서는 인증된 신원과 Originator의 결합 및 TLS가 필요하다. 관리자 값이 런타임 환경에 배포되지 않도록 운영 환경도 분리해야 한다. CSEBase의 신규 AE 등록 정책, 다른 앱의 접근, 알림 수신기의 발신자 인증까지 자동 강화하지는 않는다.

개별 허용·거부 로그와 정책 JSON을 평가 증거로 사용한다. 센서 원본의 무단 생성 방지와 대시보드의 조회 전용 권한을 설명하고, 사람의 개인정보 대신 모의 설비 데이터를 사용한다는 점 및 향후 작업자 정보가 포함될 때 접근 제한·보존 기간을 추가할 계획을 설명한다.

자동 테스트는 정책 구성과 요청 신원, 기존 HTTP 테스트 더블을 이용한 회귀 검증이다. 실제 ACME의 권한 집행을 대체하지 않는다. 현재 환경에서 사용자 VM에 연결하지 않았으므로 위 라이브 검증은 배포 환경에서 별도로 실행해야 한다.
